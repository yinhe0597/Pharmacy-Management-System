# 06 开发规范

> Go 工程实践规范，覆盖代码组织、错误处理、事务纪律、金额、日志、API、Git 与审查。
> 所有团队代码须遵循本文档；与代码评审一起作为合入门槛。

---

## §1 Go 基础

- **Go 1.26.6**（与 `go.mod` / CI 对齐），启用 `go mod`，依赖锁进 `go.sum`。
- 工具链固定：`golangci-lint` **v2.1.6**（`errcheck`、`govet`、`ineffassign`、`staticcheck`、`gocyclo`）为 CI 门槛。
  - v1.x 早于 Go 1.24，其内嵌 `go/types` 无法解析新标准库，lint 门槛会**整体失效**；
  - `.golangci.yml` 须为 **v2 格式**（`version: "2"`），否则 v2 直接报配置不兼容并退出——等于没有 lint 门槛；
  - 升级 golangci-lint 时**必须同步确认配置格式与启用项**（v2 把 QF\* 并入 `staticcheck`，门槛比 v1 更严）。
- 命名：包名小写单词；导出符号以域术语命名（`DispenseAndReduceStock` 而非 `Reduce`）。
- 类型：入参出参显式；禁止 `interface{}`（用 `any`，且尽量不用）。
- 所有跨层方法第一参数为 `context.Context`。

## §2 分层纪律

| 层 | 允许 | 禁止 |
|----|------|------|
| Handler | DTO 转换、参数绑定校验、错误码→HTTP 映射 | 业务规则、直接操作 Repository/DB |
| Service | 业务规则、事务编排、调用 Repository 与其他 Service/port | HTTP 概念、框架类型泄漏 |
| Repository | GORM 查询、事务透传 `tx` | 业务规则、循环依赖 |
| Domain | 纯类型/函数，无第三方依赖 | 导入 model/repository |

- 依赖方向严格单向：`handler → service → repository`。
- `model` 仅供 Repository 使用；`domain` 不依赖 `model`（如需，做映射）。

## §3 错误处理

### 3.1 业务错误类型

```go
// pkg/errs/errs.go
type Error struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    HTTP    int    `json:"-"` // 映射的 HTTP 状态
}
func (e *Error) Error() string { return e.Message }

var (
    ErrNotFound   = &Error{Code: 9004, Message: "资源不存在", HTTP: 404}
    ErrState      = &Error{Code: 9005, Message: "状态冲突", HTTP: 409}
    ErrStockShort = func(shortage map[int64]int64) *Error { ... } // 2001
)
```

- 业务错误用 `errs.New(code, msg, http)` 或预置变量构造；用 `errs.Is(err, target)` 判断。
- Handler 层统一 `response.Write(ctx, err)`：`err` 为 `*errs.Error` 时用其 HTTP/Code，否则 500 + 流水号。

### 3.2 纪律

- 错误必须被处理或显式包装（`fmt.Errorf("...: %w", err)`），不允许吞错。
- 日志记录在**最外层**（Handler 或 Service 事务失败处），避免重复打日志。
- 参数校验：DTO 用 `go-playground/validator` tag；业务前置条件在 Service 层用 `errs` 返回。

## §4 事务纪律（最高优先级）

1. 只有 **Service 层**可以开启事务；Repository 不主动开事务。
2. 多写操作必须单事务；禁止跨事务拆分「预占+实扣」等关联操作。
3. Repository 方法以 `WithTx(tx *gorm.DB)` 或首参 `tx *gorm.DB` 透传；事务内用同一连接。
4. 行锁写法：`db.Clauses(clause.Locking{Strength: "UPDATE"}).First(&inv, id)`。
5. 扣减库存条件更新：`db.Model(&inventory{}).Where("id=? AND quantity>=?", id, n).UpdateColumn("quantity", gorm.Expr("quantity - ?", n))`，检查 `RowsAffected`。
6. 事务函数签名返回 `error`，任一步失败整体 `Rollback`；不在事务内 `panic`。
7. 事务内禁止外部网络调用（保持事务短、避免锁持有过久）。

## §5 金额与数字

- 金额一律 `int64`（分）；禁止 `float64/float32` 参与金额计算。
- 拆零价换算走 `pkg/money` 的 `SplitPrice`，禁止各处手写舍入。
- 数量一律 `int64`；涉及 LDU 折算在 domain/rule 提供集中函数，禁止散落各处。

## §6 日志（slog）

- 使用 `log/slog`，JSON 输出，含字段：`ts level msg request_id user path duration`。
- 请求日志在中间件统一打；业务日志只打关键节点（事务提交/回滚、状态流转、预警生成）。
- 禁止打印密码、完整身份证号、银行卡号等敏感信息（脱敏函数放 `pkg/sanitize`）。

## §7 API 规范

- 统一前缀 `/api/v1`；资源命名复数名词小写；动词用子路径（`/submit`、`/review`、`/confirm-dispense`）。
- 统一响应信封 `{code,message,data}`（见 [03-接口设计.md](03-接口设计.md) §1）。
- 分页/筛选参数统一；时间统一 RFC3339；日期统一 `YYYY-MM-DD`。
- 每个 Handler 带 swaggo 注解；新接口必须能通过 `swag init` 生成文档。

## §8 Git 与提交规范

- 分支：`main` 为受保护主干；功能分支 `feat/<模块>-<简述>`，如 `feat/inventory-transfer`；修复 `fix/<简述>`。
- 提交信息：`<type>(<scope>): <subject>`，type ∈ `feat|fix|refactor|docs|test|chore`；
  首行 ≤72 字符，正文说明 why。
- **主页 README 同步（强制）**：每次提交必须同步更新仓库主页 `README.md`
  （功能概览 / API 端点 / 迁移版本数 / 状态里程碑 / 文档索引），保证 Gitee/GitHub 首页
  与代码实际能力一致；变更明显影响对外形态时同版本号一并更新。
- 合入 `main` 前必须：`golangci-lint run` 通过、`go test ./...` 通过、CI 全绿、代码审查通过。
- 迁移脚本单独提交（`migrations/`），禁止把 DDL 塞进业务提交。
- **主干分支名以仓库实际为准**：本仓库主干为 `main`（历史上是 `master`，2026-09-29 统一改名）。
  CI 的 `on.push.branches` 必须与之一致——此前两条流水线都只配了 `main` 而推送走 `master`，
  导致流水线整体不触发，「CI 全绿」一度只是形式要求。改名须同步
  `.github/workflows/ci.yml`、`.github/workflows/frontend-ci.yml`、`.workflow/docker-image.yml`。
- **前端必须在 CI 内**：`.github/workflows/frontend-ci.yml` 执行
  `npm ci` / `type-check` / `lint` / `format:check` / `test` / `build`。
  前端门禁若只靠本地自觉，等于没有门槛。`test` 内含前后端字段契约守卫，
  该守卫依赖 `../internal`（要读后端 struct 的 json tag），因此必须 `actions/checkout`
  整个仓库，不能只 checkout `pharmacy-web/`。

## §8.1 前后端字段契约（强制）

后端 struct 的 `json` tag 是字段契约的**唯一定义处**。新增/改名任一响应字段时，
必须同步前端渲染处，且由 `pharmacy-web/src/types/contract.test.ts` 守卫：
模板中静态绑定的 `el-table-column prop="X"` 若在后端任何 struct 中都不存在，
测试直接失败并指出文件与列名。

- 契约来源取 `internal/` 下所有 Go struct 的 json tag，**不要用 `docs/swagger.json`**：
  多数 handler 走泛型 `Body` 返回，swag 不会为其生成 definition，用 swagger 会产生 61 个误报。
- 该守卫只能证明「字段在后端某处存在」，不能证明「存在于该端点返回的 DTO 中」。
  跨表展示字段（药品名、库房名等）必须由仓储层 JOIN 后经**行 DTO** 返回，
  并在后端补集成测试锁死，参见 `internal/repository/inventory_repo.go` 的
  `InventoryRow` / `StockAlertRow`。

## §9 测试纪律

- 单元测试与被测代码同包或 `_test` 包；命名 `Test<Method>_<Case>`。
- Repository 测试用 mock（`go-sqlmock`）或真实 PostgreSQL（`tests/` 集成测试）。
- 关键正确性路径（预占/实扣/释放、拆零、状态机、效期判定）必须有测试兜底（见 [07-测试方案.md](07-测试方案.md)）。
- 覆盖率门槛（`scripts/check_coverage.sh`）：domain ≥ 85%；集成口径 service ≥ 35%、repository ≥ 20%、handler ≥ 10%；单元口径 middleware ≥ 30%、pkg/auth ≥ 60%、pkg/money ≥ 60%、config ≥ 30%。
- **集成测试必须连独立测试库**：`setupTestDB` 会对 `testCleanupTables` 逐表
  `TRUNCATE ... RESTART IDENTITY CASCADE`，指向开发库会直接抹掉本地数据。
  库名默认 `yaofang_test`（`YF_TEST_DB_NAME` 可覆盖），首次使用执行
  `make test-db-init` 建库并跑完迁移。CI 里用一次性容器库，显式指定同名即可。
- 反向验证不可省：写完「修好了」的测试要**先确认它能失败**——把修复临时改回去，
  确认测试红，再改回来。只跑通一次的测试可能根本没测到东西。
- 断言优先用带上下文的比较（如 `got != want` 附期望值）而非裸 `Error()`，
  否则失败时只得到一句「为空」，无法判断是哪个字段、期望多少。

## §10 代码审查清单

- [ ] 分层是否正确（无跨层访问）
- [ ] 多写操作是否单事务；扣减是否有条件更新兜底
- [ ] 状态流转是否只经 Service 方法
- [ ] 金额是否为整数分；有无手写舍入
- [ ] 错误是否传播/包装，有无吞错
- [ ] 敏感数据是否脱敏
- [ ] 新表/新字段是否有迁移脚本
- [ ] Handler 是否有 Swagger 注解
- [ ] 关键逻辑是否有单元测试

## §11 GORM 建模与列名规范

> 历史问题记录：GORM 命名策略会把 Go 字段 `VPBBatch` 转成 `vpb_batch`（V-P-B 错位），
> 导致 42703（column does not exist）。已在 `model/drug.go`、`model/reference.go` 通过
> `gorm:"column:vbp_batch"` 显式指定修复，详见 [00-项目状态速查.md](00-项目状态速查.md)「已知坑位」。

### 11.1 列名生成规则（GORM 默认命名策略）

- 字段名按「大写字母边界」拆词转下划线小写：`BatchNo` → `batch_no`、`UnitPrice` → `unit_price`。
- **连续多个大写字母（缩写）不会逐字拆开**：`VPBBatch` 被当作 `V-P-B` 连续大写，仅在大写转小写处
  插入下划线，得到 `vpb_batch`，与预期的 `vbp_batch` 错位。
- 已知缩写（API/ID/URL/JSON 等）会被 GORM 规范化后转换，但业务缩写（VBP/VPD/FEFO 等）不在列表内，
  一律按上述规则处理。

### 11.2 建模要求

1. **新字段一律核对列名**：含连续大写缩写（VBP/VPD/FEFO/NMPA/QC 等）的字段，务必确认 GORM 生成的
   列名与迁移 SQL 一致；不一致时显式 `gorm:"column:xxx"` 指定。
2. **迁移 SQL 是唯一事实来源**：模型 tag 只作为 GORM 查询映射，最终列名以 `migrations/*.up.sql` 为准；
   两者不一致会在运行时产生 42703。
3. **全量审计**：新增/修改模型后，可临时跑全模型列名比对（`schema.Parse` vs `information_schema`），
   确保 0 错位（参考 [00-项目状态速查.md](00-项目状态速查.md) 的审计提示）。
4. **已修复案例**（勿回退）：`Drug.VPBBatch`、`VBPDrug.VPBBatch` 必须保留 `column:vbp_batch` tag。

## §12 安全基线

> 以下为**必须遵守**的安全红线，实现以代码为准（config/middleware/server），评审时逐条核对。

1. **JWT 密钥强度（`internal/config/config.go`）**：`release` 模式强制 ≥32 位随机 JWT 密钥；空值、默认值、弱/占位密钥
   （`change-me` / `change_me` / `change.me` / `changeme` / `placeholder` / `please-change` / `please_change` /
   `yaofang-dev-secret` / `yaofang-compose-dev-secret` / `yaofang-secret` / `your-secret` / `example-secret` /
   `sample-secret` / `test-secret` 及其子串变体）一律在 `config.validate()` 拒绝启动。禁止在配置文件/编排中回填弱默认值。
2. **可信代理（`internal/server/server.go`）**：`server.trusted_proxies` / `YF_SERVER_TRUSTED_PROXIES` 默认不信任任何代理头
   （`ClientIP` 取直连地址），防止伪造 `X-Forwarded-For` 绕过登录限速；部署在 Nginx/网关之后必须显式配置代理所在网段
   （如容器网段 `172.16.0.0/12`）。
3. **CORS（`internal/middleware/cors.go`）**：`server.cors_allow_origins` 留空 = 不下发任何 CORS 头（fail-closed）；
   仅显式配置 `*` 或具体域名白名单才放行；`release` 模式下对 `*` 放行会告警，生产应限定域名。
4. **Swagger 与探针（`internal/server/server.go` / `health.go`）**：Swagger 仅非 `release` 模式注册；`/readyz` 只回显
   通用状态串（`database_unreachable` / `sql_db_unavailable`），不回显数据库底层错误细节，避免泄露。
5. **每请求复查用户状态与角色（`internal/middleware/middleware.go`）**：`Auth` 经 `UserStateChecker` 对每个请求复查
   数据库当前状态与角色（停用/删除返回 `9002 未认证` 拒绝访问；登录时账号停用由 `9009` 拦截），角色取数据库当前值，
   停用/删除/降权在 JWT TTL 内**立即生效**；`RequireRoles` 用复查后的角色做白名单断言，不得依赖签发时缓存的旧角色。
6. **并发纪律（最高优先级）**：
   - 多行写必须**单事务** + **条件更新**（`UPDATE ... WHERE 余额/数量 >= ?` 并检查 `RowsAffected`）双保险；
   - 唯一键并发写入必须用 **`ON CONFLICT` upsert**（依赖唯一约束），禁止「先查后插 + 冲突后回退」——
     PostgreSQL 唯一键冲突后事务即 `aborted`（25P02），随后的回退查询必然失败；
   - 多行加锁须按**同一全局顺序**（如 `inventory_id` 升序）加锁，避免反向并发死锁；
   - 重复执行型任务（定时预警、调度重入）必须以**唯一索引 + `ON CONFLICT DO NOTHING`** 保证幂等，
     不得只靠「先查后写」两步判断。
7. **默认口令不得上线（`internal/server/startup.go`）**：启动时检查是否仍有启用账号使用种子默认口令
   `admin123`；`release` 模式命中即**拒绝启动**（`YF_AUTH_ALLOW_DEFAULT_PASSWORDS=true` 仅限演示环境豁免），
   其他模式打印告警并列出账号。与弱 JWT 密钥拦截同一设计原则：默认凭据不得静默上线。
8. **写操作审计（`internal/middleware/audit.go`）**：所有已认证的非只读请求（POST/PUT/PATCH/DELETE）统一落
   `operation_logs`（动作名取子资源动作如 `dispense`/`void`/`complete`，记录路由模板、`resource_id`、IP、状态码）；
   **禁止把请求体写入审计日志**（避免口令/病历正文入库）。新增写接口无需额外埋点即自动纳入审计。
9. **数据库迁移（`scripts/migrate.sh`）**：迁移由 `schema_migrations` 版本表驱动、按文件增量执行、单文件单事务；
   重复执行只跳过，不得回到「全量重放 `*.up.sql`」的老做法（已初始化的库二次执行必然失败）。
   历史库（旧版重放方式初始化）首次升级须显式指定一次 `YF_MIGRATE_BASELINE_TO=<已部署版本号>` 建立基线。
10. **金额与事务读一致性**：
    - 金额一律整数分运算，解析外部输入用 `money.ParseYuan`（十进制字符串，不走浮点）；
      拆零取整采用半入口径，存在已知累计残差（见 docs/04 §1.1）；
    - 事务内不得使用服务自身的根连接再查询（应透传 `tx`），否则读到事务外快照并额外占用连接、拉长行锁持有时间。
