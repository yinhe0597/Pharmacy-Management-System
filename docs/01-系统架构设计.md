# 01 系统架构设计

> 技术栈：Go 1.26+ / Gin / GORM / PostgreSQL 14+ / golang-migrate / swaggo / JWT / robfig-cron

---

## 1. 总体架构

模块化单体：一个可执行程序，内部按业务模块组织代码，模块之间通过 Service 层调用。
一期「药房」能力直接实现，二期「诊疗」能力通过接口抽象接入。

```
┌──────────────────────────────────────────────────────────────┐
│                        表示层 Handler                        │
│   HTTP / Gin 路由 · 参数校验 · DTO 转换 · JWT 鉴权 · 错误映射  │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                      领域服务层 Service                      │
│  drug · supplier · inventory · prescription · specialdrug   │
│  pharmaservice · report · purchase                           │
│  业务规则 · 状态机 · 事务编排（唯一允许操作 DB 的层）           │
│   ┌────────────────────────────────────────────────────┐     │
│   │ service/port（对外接口）                            │     │
│   │ IPatientService · IStockService · IPricingService  │     │
│   └────────────────────────────────────────────────────┘     │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                        仓储层 Repository                     │
│   GORM · 表操作封装 · 事务透传（tx）· 行级锁                   │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                        PostgreSQL 14+                        │
└──────────────────────────────────────────────────────────────┘
```

**分层约束（强制）：**

| 层 | 职责 | 禁止 |
|----|------|------|
| Handler | 请求解析、校验、DTO↔模型转换、鉴权 | 不写业务规则、不直接操作 DB |
| Service | 业务规则、状态流转、事务边界、调用 Repository | 不出现 HTTP 概念 |
| Repository | 单表/聚合持久化操作 | 不写业务规则 |
| Domain | 纯结构体、状态机定义、金额/规则 | 无任何依赖 |

## 3. 模块划分

| 模块 | Service | 核心能力 |
|------|---------|---------|
| 药品 drug | DrugService | 主数据 CRUD、一药多规/一品多商、分类/分级/管制标记、配伍禁忌维护、启停用 |
| 供应商 supplier | SupplierService | 供应商信息维护、药品-供应商供货关系、供货价 |
| 采购 purchase | PurchaseService | 采购计划建议、采购单、收货质检入库（绑定批次） |
| 库存 inventory | InventoryService | 入库/出库/调拨/拆零/调整、预占/释放、效期与上下限预警、盘点、流水 |
| 领用/补发登记 requisition | InventoryService（`requisition_service.go`） | 领用/补发登记单（多明细，FEFO 扣减，不计费） |
| 处方 prescription | PrescriptionService | 录入、审核（配伍/极量/重复用药）、批号调配、发药确认、退药、状态机 |
| 特殊药品 specialdrug | SpecialDrugService | 麻精五专、专用处方登记、空安瓿回收、专账 |
| 药学服务 pharmaservice | PharmaService | 用药咨询、不良反应、用药指导 |
| 交互引擎 interaction | InteractionService | 4 策略分层匹配（显式→成分→分类→标签）+ 患者个体化禁忌 |
| 诊疗 clinical | ClinicalService | 诊疗项目目录、计费（手工/处方一键/红冲）、患者费用 |
| 参考数据 reference | ReferenceService | ICD-10/集采/医保/耗材/非医保目录查询与目录匹配 |
| 报表 report | ReportService | 进销存汇总、效期分析、特殊药品统计、调配工作量、拆零统计、患者费用 |
| 系统设置 setting | SettingService | 系统参数（默认诊费等） |
| 操作日志 operationlog | OperationLogService | 统一操作审计日志（用户/动作/时间筛选） |
| 二期就诊 clinical2 | VisitService / MedicalRecordService / ChargeService | 就诊（挂号/分诊/接诊/退号）、病历（多诊断）、合并结算（收费/退费） |
| 用户/鉴权 auth | AuthService | 用户管理、角色、登录、JWT |
| 患者 patient | PatientService（`service/patient`） | 患者档案、过敏史、用药史（已完整实现） |
| 计价 pricing | SimplePricingService（`service/pricing`） | 药品/耗材/诊疗项目计价，二期合并结算调用 |

模块间依赖方向：`prescription → inventory`、`prescription → specialdrug`（特殊处方）、
`report → inventory/prescription`。均为 Service 层方法调用，不跨层访问。

## 4. 事务与并发设计（核心）

> 库存正确性是本系统第一优先级，规则详见
> [04-领域模型与业务规则.md](04-领域模型与业务规则.md)。

### 4.1 事务边界

- 所有「多行写」操作必须在 Service 层用一个事务完成：预占、实扣、释放、
  处方状态流转 + 库存变更、拆零、调拨（双端）、盘点调整。
- Repository 方法签名统一支持传入 `*gorm.DB`（`WithTx` 透传），避免嵌套事务。

```go
// 示例：发药实扣
err := s.db.Transaction(func(tx *gorm.DB) error {
    invRepo := repository.NewInventoryRepo(tx)
    for _, disp := range dispenseList {
        inv := invRepo.LockForUpdate(ctx, disp.InventoryID) // SELECT ... FOR UPDATE
        if inv.AvailableQuantity() < disp.Qty {
            return errs.InventoryNotEnough(...)
        }
        invRepo.Deduct(ctx, disp.InventoryID, disp.Qty) // WHERE quantity >= disp.Qty
        invRepo.CreateTransaction(ctx, txn)             // 写流水
    }
    prescRepo.UpdateStatus(ctx, ...)                     // 状态流转
    return nil
})
```

### 4.2 并发防护（双保险）

1. **行级锁**：对 `inventory`、`prescriptions` 行 `SELECT ... FOR UPDATE`，串行化并发写。
2. **条件更新**：`UPDATE inventory SET quantity = quantity - ? WHERE id = ? AND quantity >= ?`，
   检查 `RowsAffected`，防止因业务逻辑漏洞出现负库存。
3. **乐观版本**：`prescriptions.version` 字段 + `WHERE version = ?`，防止重复发药/重复退药。

### 4.3 预占/实扣/释放模型

- 预占：锁库存行 → 校验 `可用 = 数量 - 已预占` → `reserved_quantity += n` → 写 `stock_reservations` 记录。
- 实扣（发药确认）：锁库存行 → `quantity -= n`、`reserved_quantity -= n` → 流水（type=dispense）→ 预占记录置 consumed。
- 释放（退方/驳回/作废）：锁库存行 → `reserved_quantity -= n` → 预占记录置 released。

### 4.4 幂等与唯一约束

- 操作号（流水号、单号）用 `操作类型 + yyyyMMdd + 序号` 生成，DB 加唯一约束兜底。
- 发药记录 `(prescription_item_id, inventory_id, batch_no, 唯一ID)` 防重复入账。

## 5. 请求链路与中间件

```
请求 → RequestID → 访问日志(slog) → Recover → JWT 鉴权 → 路由 → Handler → Service → Repository → DB
                                                                          │
                                                             响应封装 {code,message,data}
```

中间件职责：

| 中间件 | 职责 |
|--------|------|
| RequestID | 生成/透传请求 ID，写入日志上下文 |
| Logger | 记录方法、路径、耗时、状态码、请求ID（脱敏） |
| Recover | panic 捕获 → 500 兜底，避免进程退出 |
| Auth | 解析 JWT，注入 `ctx.User`；白名单路由除外 |
| RBAC | 按角色限制路由（如盘点、专账仅管理员/指定角色） |

## 7. 定时任务（scheduler）

| 任务 | 周期 | 行为 |
|------|------|------|
| 效期预警扫描 | 每日 | 扫描 `inventory`，近效期（≤ 预警天数）生成 `stock_alerts`，过期批次自动锁定 `status=2` |
| 过期批次锁定 | 每日 | 兜底：`expiry_date < today` 的可用库存锁定并禁止发药 |
| 库存下限预警 | 每日 | 可用库存（含整盒/拆零折算）低于下限 → 生成补货预警 |
| 采购计划建议 | 手动触发 | 基于上下限 + 近 30 日消耗生成建议采购量 |

预警结果落地 `stock_alerts` 表，可通过 API 查询/处理，不依赖消息队列。

## 9. 关键设计原则（总结）

1. **库存操作必须事务化**：预占、实扣、释放在同一事务 + 行锁。
2. **批号效期贯穿全流程**：收货即绑定，发药按 FEFO，退药按原批次回补。
3. **接口隔离**：诊疗相关能力定义在 `service/port`，一期简易实现，二期替换。
4. **状态机明确**：处方、库存批次、单据均有明确状态与流转入口（Service 层方法）。
5. **金额整数化**：一律以「分」存储计算，杜绝浮点误差。
6. **分层单向依赖**：Handler → Service → Repository → DB，禁止跨层。
