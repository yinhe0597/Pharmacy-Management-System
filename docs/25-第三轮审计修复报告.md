# 25 第三轮审计修复报告（复核 + 收尾）

> 目的：复核第二轮审计修复（v1.4.0 提交集）的**落地质量**，补齐遗留项，并把「部署运维」链路真正做成可重复执行。
> 时间：2026-09-12 ｜ 方式：逐提交 diff 复核 + 真实 PostgreSQL 16 实测（33 个迁移）+ HTTP 冒烟 + 门禁全跑。
> 结论：**发现并修复 2 个由加固引入的回归、1 个部署阻断项、8 组遗留项**；全部门禁与端到端实测通过。

## 一、复核发现的问题（按严重度）

### 1.1 回归：本地起库流程被破坏（高）

compose 移除弱默认值后 `YF_DATABASE_PASSWORD` / `YF_AUTH_JWT_SECRET` 成为必填，
而 compose 会对**所有服务**做变量插值——即使只执行 `docker compose up -d db` 也会报错：

```
error while interpolating services.api.environment.YF_AUTH_JWT_SECRET: required variable ... is missing
```

`Makefile` 的 `db-up`、README 的本地起库说明未配套 → 文档推荐流程不可用。

**修复**：新增 `make env-init`（优先 `openssl rand`，回退 `/dev/urandom`，生成 ≥32 位 JWT 密钥 +
随机数据库口令、权限 600 的 `.env`），`db-up`/`docker-up` 自动依赖它；新增根 `.env.example`；
README/docs/10 补充说明。

### 1.2 回归：集成测试与 CI 无法加载配置（高）

弱密钥拦截生效后，`config.Load()` 在**没有 `configs/config.yaml` 的环境（CI）** 使用 viper 默认
占位密钥 `change-me` → 直接报错，集成测试全部失败；本地 `config.yaml` 亦为被拉黑的占位值。

**修复**：`setupTestDB` 内 `t.Setenv("YF_AUTH_JWT_SECRET", ...)` 注入测试专用强密钥（CI 零依赖）；
本地 `configs/config.yaml` 更新为强随机密钥，并与 `.env` 的数据库口令对齐。

### 1.3 部署阻断：迁移仍是「全量重放」（高，第二轮遗留未修）

compose（dev/prod 的 `migrate` 服务）、`deploy/migrate.sh`、`Makefile db-migrate`、CI 均为
`for f in migrations/*.up.sql; psql -f` 的全量重放。该方式**只在全新库上成立**：

- 已初始化库二次执行 → `CREATE TABLE ... already exists` 失败；
- `backend` 依赖 `migrate` 的 `service_completed_successfully` → **升级/重启即阻断启动**。

**修复**：新增 `scripts/migrate.sh`：

| 能力 | 说明 |
|------|------|
| 版本表 | `schema_migrations(version PK, applied_at)`，按文件名记录 |
| 增量执行 | 仅应用未记录的迁移；重复运行输出 `skip`（幂等） |
| 事务安全 | 单文件 `--single-transaction`，失败整体回滚，不留半应用状态 |
| 历史库引导 | 检测到「有 `users` 表但无版本记录」时**拒绝猜测**，要求一次性 `YF_MIGRATE_BASELINE_TO=000032`（只写版本记录、不执行 SQL） |

五个入口统一接入：`docker-compose.yml`、`docker-compose.prod.yml`、`deploy/Dockerfile.migrate`、
`Makefile db-migrate`、`.github/workflows/ci.yml`。

**实测**：对已初始化的库以 `000032` 建立基线 → 仅应用 `000033`；再次运行 → 全部 `skip`（版本记录 33 条）。

### 1.4 修复缺测试守护（中）

第二轮的 upsert / 条件更新 / 盘点差异属「并发正确性命门」，却无任何测试：

- `ON CONFLICT ... RETURNING *` 的回填行为决定流水 `before/after` 正确性；
- 采购超收护栏依赖「同一条 UPDATE 内条件 + 累加」。

**修复**：新增 `internal/repository/concurrency_sql_test.go`（**DryRun 断言生成的 SQL**，零依赖）与
`internal/service/audit_fix_integration_test.go`（真实 PG：4 并发入库同批次、超收双护栏、盘点差异口径）。

### 1.5 测试隔离缺陷：用例顺序相关（中）

`setupTestDB` 的清空表清单不含 `stocktakes`，盘点用例把库房置为 `counting` 后，
后续入库用例报「盘点进行中，禁止库存变动」——单独运行并发入库用例会失败。

**修复**：清空清单补齐（盘点/拆零单/领用单/专账等），盘点用例结束取消盘点；
单独运行、整包运行、乱序运行均通过。

### 1.6 备份脚本在无人值守场景挂起（中）

`scripts/backup_db.sh` 在 PATH 存在 `pg_dump` 但无口令时，会停在交互式口令提示（实测 300s 超时无输出），
不适合 crontab 场景。

**修复**：`pg_dump -w`（禁止交互提示，快速失败）→ 失败回退容器内 `pg_dump`；脚本自动读取部署目录 `.env`。
**实测**：直连路径 296 KB dump、回退路径 292 KB dump，均成功。

### 1.7 其余遗留项（第二轮已识别未修，本轮补齐）

| 项 | 问题 | 修复 |
|----|------|------|
| 预警去重 | `HasOpenByKey` 预查询 + `Create` 非原子，且「低于下限」以 `'ALL'` 查询、以空串写入（**键错配 → 每次调度新增重复预警**） | 迁移 `000033` 建 `open` 状态部分唯一索引（历史重复先清理）+ 仓储 `CreateIfAbsent`（`ON CONFLICT DO NOTHING`）；查询/写入键统一为空批次 |
| 患者档案 mass-assignment | 直接绑定 `model.Patient` + `Select("*")` 全量更新 | 引入 `patientWriteRequest` 白名单 DTO；仓储改显式列 + map 更新（仍支持布尔/文本清零） |
| 空安瓿核对人 | `VerifyAmpouleReturn` 只改内存 `VerifiedBy`，从不落库（五专审计字段丢失） | `AmpouleReturnRepo.Verify` 一并写 `verified_by`，仅 `pending→verified` 且幂等（重复核对返回 `9005`） |
| 事务内跨连接读 | `Submit` 内 `AvailablePacks`、`Review` 内交互检测均走根连接（读事务外快照 + 拉长行锁持有） | 新增 `availablePacksTx`，`CheckPrescription` 接受 `db` 句柄并由 `Review` 传入 `tx` |
| 调拨锁序 | 按请求顺序加锁，反向并发调拨可交叉等待死锁 | 按 `inventory_id` 升序加锁（全局统一顺序） |
| 退药顺序敏感 | 整盒记录优先被消费，散片退药误报 `3013` | 发药记录查询改「拆零优先」（`is_split DESC`） |
| 金额工具 | `ItemAmount` 在 `packSize<=0` 时除零；`FromYuan` 用 float64 | `packSize<=0/==1` 显式分支；`FromYuan` → `ParseYuan(string)` 十进制精确解析 |
| CORS 说明 | 注释称「为空或 `*` 放行任意来源」，与实现（空白名单 = 不下发头，fail-closed）不符 | 修正注释并补 4 项单测锁定行为（原判定为文档错，代码本身安全） |
| 写操作审计覆盖 | 仅登录/改密/建用户写 `operation_logs`；发药/盘点/红冲/结算/改设置等敏感操作无审计 | 新增 `middleware.AuditWrites`：所有已认证非只读请求落审计（动作名细化为 `dispense`/`confirm-dispense`/`return`/`void`/`complete` 等，记录路由模板/`resource_id`/IP/状态码，**不记请求体**） |
| 默认口令上线风险 | 种子账号 `admin123` 可静默上线 | 新增启动门禁 `server/startup.go`：`release` 模式下仍存在默认口令启用账号则**拒绝启动**（`YF_AUTH_ALLOW_DEFAULT_PASSWORDS=true` 仅限演示）；其他模式告警并列出账号 |

## 四、遗留与建议（未阻塞）

1. `prescriptions.patient_id` 仍无数据库外键（服务层已校验患者存在）；如需落 FK，需将字段改为可空指针并配套迁移。
2. 登录限速为**进程内计数**（5 次/分钟，键 = 客户端 IP + 用户名）：多副本部署各副本独立计数，
   建议在网关层再限速或接入共享存储；反向代理场景必须配置 `YF_SERVER_TRUSTED_PROXIES` 才能取到真实 IP。
3. 前端依赖分包后 `element-plus`/`echarts` 仍各约 1.1 MB（总量未降），可进一步做 ECharts 按需引入。
4. PostgreSQL 兼容性物证为 PG16（迁移与集成测试均实测 PG16）；PG14/15 未实测，如需支持请补矩阵验证。
5. `service`/`handler`/`repository` 覆盖率尚无门槛（当前靠集成测试覆盖关键路径），可后续补门槛。
6. 二期就诊模块 S7（合并结算报表）仍待实施（见 docs/20）。
