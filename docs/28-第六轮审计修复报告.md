## 三、Critical：业务正确性

### 3.1 收货质检门禁失效（GSP 合规破口）

`PurchaseReceiptItem.QCResult` 同时带 GORM `default:1` 与 DDL `DEFAULT 1`。
GORM 对带 `default` 的零值字段会省略该列，落库时取 DB 默认值——于是「未质检(0)」被改写为「合格(1)」。
`HasUninspected`（`qc_result NOT IN (1,2)`）**恒为 false**，收货单可在零质检下入库。

- **修复**：模型去掉 `default` tag；迁移 `000037` `DROP DEFAULT`（**不回溯改写历史行**——无法区分「真合格」与「未登记」，贸然改成 0 会把真实合格单误判为未质检并阻断已入库单据）。
- **收口**：`Receive` 增加 `qc_result ∈ [0,2]` 取值域校验，避免非法值绕过两道门禁永久挂在「未质检」上。

### 3.2 库存调拨负数量 → 源库房库存凭空增加

`Transfer` 未校验 `Quantity > 0`。负数时 `Available() < qty` 恒真通过，
`Deduct` 生成 `quantity = quantity + N`，源库房增库存且 `transfer_out` 流水记为**正数**（伪入库），
目标端因 `if e.Quantity <= 0 { continue }` 被跳过 → 净虚增，无流水对账。

- **修复**：service 入口加正数校验 + `Deduct`/`DeductAvailable` 仓储层 `qty <= 0 → false` 防御断言（双层）。

### 3.3 红冲净额变负

`VoidCharge` 置原单 `voided=true` 并新增 `Amount=-X, Voided=false` 的冲正单。
下游（`CalculateBill` ②、`PatientCharges` 报表）只按 `voided=FALSE` 过滤，
于是只捞到 `-X` —— 患者净额凭空减少一笔，结算甚至因 `payable < 0` 被阻断。

- **修复**：冲正单同步置 `voided=true`（两单成对，净额归零），审计留痕由冲正单记录本身承担。
  退药产生的负额单（`ref_type='prescription'`）**不受影响**，仍是有效冲减。

### 3.4 自动拆零处方的退药回补到整盒行

`need_split` 发药记录按**拆零形态（片）**计量，但 `rec.InventoryID` 仍指向被拆开的**整盒行**。
退药时按该 ID 回补，把「片」写进以「盒」计量的行 → 库存虚增一个整盒（15 片 = 12+3 的场景实测虚增）。

- **修复**：`rec.IsSplit && !inv.IsSplit` 时改定位同批次**拆零行**；拆零行不存在则按拆零口径重建（进价取批次折算价，与发药侧同源）。
- **反向验证**：还原修复后回归测试报 `拆零应为 17 片，got 16`，端到端症状为「批次分配不足，无法调配」。

## 四、High 级修复（19 项）

### 4.1 效期口径（date-only）—— 同一根因，4 条路径 3 种结论

`expiry_date` 是 `DATE` 列，PostgreSQL 按会话时区把它提升为**当天 00:00** 再与参数比较。
原实现传 `time.Now()`（带时分秒），实测：

| expiry_date | `>= now()`（原实现） | `>= CURRENT_DATE`（正确） |
|-------------|---------------------|--------------------------|
| 昨天 | f | f |
| **今天** | **f ← 被排除** | **t** |
| 明天 | t | t |

由此当天到期批次出现**自相矛盾**：

| 代码路径 | 对「今天到期」批次的判定 |
|---------|---------------------|
| FEFO 发药筛选 `expiry_date >= now()` | **取不到**（无法发药） |
| `LockExpired` 同一参数的 `<` 比较 | **判为已过期并锁定** |
| `rule.IsExpired`（date-only） | 未过期 |
| `rule.IsNearExpiry` | 近效期 |

**修复**：
- `FindAvailableForDispenseUnit` / `FindAvailableForDispense` / `LockExpired` 改用 `CURRENT_DATE`，
  并**移除 `today time.Time` 形参**——从签名层面消除该陷阱（10 个调用点同步更新）。
- `todayNow()` 归一化为 **Asia/Shanghai 当天零点**：效期是 date-only 语义；
  且容器 TZ 常为 UTC，与 DSN 钉定的 `Asia/Shanghai` 会差最多 8 小时、跨零点时业务日错一天。
  归一化后即使被误当 SQL 参数传下去也依然正确。

### 4.2 GORM 零值更新（两个「已确认功能不可用」的断链）

| 位置 | 问题 |
|------|------|
| `drug_repo.go:56` | `Model(d).Omit(...).Updates(d)` 用**结构体**更新，GORM 跳过全部零值字段 → **药品无法停用**（`SetStatus(0)` 静默无效）、无法关闭拆零、无法清零零售价 |
| `clinical_repo.go:40` | `Select("*")` 但**无 `Omit`** → PUT 漏传 `code` 写空串（UNIQUE NOT NULL），第一次 PUT 毁掉编码、第二次必然唯一键冲突 |

**修复**：统一为 `Omit("id","code","created_at").Select("*")` 写法（与 `prescription_repo.go` 既有正确范式一致）。同型的 `supplier_repo` / `pharmaservice_repo` 一并对齐。

### 4.3 处方状态流转抹除审核痕迹

`UpdateStatus` 用 `map` **无条件写入** `reviewed_at` / `auditor_id` / `checker_*` 等。
调配阶段若传入未回填的 `*Prescription`，`"reviewed_at": nil` 会把已记录的**审核时间与审核人清空**——处方是核心医疗文书，审核痕迹被静默销毁。

**修复**：仅在调用方回填了值时才写入对应列。

### 4.4 局部更新清空用户角色 → 账号静默锁死

`UpdateUser` 无条件 `u.Role = role`，而 `role` 在契约中是可选字段。
`PUT /users/:id {"status":0}` 省略 role 即写入空串 → `RequireRoles` 全线 403，且无 API 可恢复。

**修复**：`name`/`role`/`phone` 空串表示「不修改」。

### 4.5 JWT 无服务端吊销（30 天有效窗口）

改密 / 管理员重置口令**不吊销已签发 token**，默认 TTL 720h。令牌泄露后，事件响应方的「改密」无法处置该令牌。

- **修复**（迁移 `000039`）：新增 `users.token_version` 签入 claims 并逐请求比对；
  `UpdatePassword` 与管理员重置口令时自增，即一次性作废该用户全部存量 token。
- **附带修正**：`role` / `username` / `name` 改为**一律取库中当前值**——此前取 token 旧值，导致改名后操作日志归属失真。
- **端到端实证**：登录 → 改密 → 旧 token 立即 **401** → 新口令登录正常。

## 五、三项架构决策落地

### 5.1 统一记账口径：选定唯一记账凭证

**决策依据（项目事实，非偏好）**：`charge_records` **没有 `visit_id` 列**，因此它无法回答「本次就诊花了多少钱」。
这正是原实现只能用 `patient_id + 时间窗口 ∈ [挂号, 结束]` **猜归属**的根因——同一患者在窗口内其它就诊的计费项会被并入本次结算。
而 `charge_items` 的 DDL 注释本就写着其 `item_id` 可指向 `charge_records.id`，
说明原设计意图即「`charge_records` 为明细来源、`charge_items` 为凭证行」。

**选定**：`charges`（结算单）+ `charge_items`（费用行）= **唯一记账凭证**。
`charge_records` 降级为「应收计费项目源」，只被结算单消费，**不被任何报表直接统计**。

迁移 `000040` 的连锁修复：

| 改动 | 解决的问题 |
|------|-----------|
| `charge_records` += `visit_id`（+ 回填历史处方来源行） | 结算单可按就诊**精确**归集 |
| `CalculateBill` ② 改按 `visit_id` 取 | 消除跨就诊错归集 |
| ② 放开 `item_type` 排除 `drug` | **修掉「手工药品费永远不进账单」的收入漏记** |
| ② 排除 `ref_type='prescription'` | 处方药费已由 ① 按快照计入，避免**重复计费** |
| `charge_items` += `source_record_id` | 消除 `item_id` 多态引用（可能指向三类不同表）缺乏判别字段的歧义 |
| `PatientCharges` 改读 `charges`+`charge_items`（限 `status='paid'`，按 `COALESCE(paid_at, created_at)` 归期） | 两张报表同源同口径，不再各自为政 |

**一个必须承认的取舍**：只认 `visit_id` 会让**不传该字段的录入方静默漏计费**——对药房账目而言比错归集更危险。
因此保留**仅对 `visit_id IS NULL` 存量行**的时间窗口回退（明确标注为过渡路径），
同时补上写入路径：手工计费弹窗新增「关联就诊」远程选择器。存量清空后该分支自然失效。

### 5.3 业务单号多副本安全（号段表）

**背景**：原实现为「前缀 + Unix 秒 + 进程内 3 位自增」，只在**单进程内**唯一。
同一秒内若两个副本各自产生第 N 条单号即得到完全相同的单号，撞 UNIQUE 约束；
而 PostgreSQL 下唯一冲突会把事务置入 `aborted(25P02)`，**整笔业务（含库存扣减）回滚**。

**选定方案：号段表**。单条 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 原子申请一段号，
进程内独占该区间 → 不同副本拿到的区间必然不相交 → 全局唯一。DB 往返摊薄到 **1/256**。

格式：`<prefix><yyyyMMddHHmmss><8 位绝对序号>`，**保留「单号可按时间排序」**这一药房现场运维刚需。
与旧格式（前缀 + 10 位秒 + 3 位序号 = 前缀后 13 位）长度不同，**不可能与存量单号冲突**。

其它方案的否决理由（针对 5~20 副本场景）：

| 方案 | 否决理由 |
|------|---------|
| `nextval()` 每单一次 | DB 往返比号段表贵 10~20 倍 |
| Snowflake / 实例 ID 后缀 | 依赖稳定实例身份；K8s 中 POD 名随重启变化，跨节点时钟偏移直接破坏单调性 |
| UUID | 破坏 `VARCHAR(30)` 列宽约束，且完全丧失可排序性 |

`Next` 改为返回 `error`：**宁可让调用方失败，也绝不静默产生可能重复的单号**。
号段大小与前缀常量集中在 `internal/pkg/seq`，启动时由组合根 `server.NewApp` 注入。

### 5.4 软删与唯一约束的系统性冲突（迁移 000038）

`000014` 给 17 张表补了 `deleted_at`（软删），但 `000001`/`000007` 的唯一约束是**全表**唯一。
软删只是标记，行仍在表内 → 编码被永久占用；而创建路径的「是否重复」预检走默认作用域（`deleted_at IS NULL`）查不到软删行，
预检通过 → INSERT 撞 23505 → 非业务错误 → **接口返回 500 而非 409**。

- **修复**：11 张业务主数据表改为部分唯一索引 `WHERE deleted_at IS NULL`（沿用仓内 000031/000033 已验证范式）。
- **刻意不转**：`visits.visit_no`、`charges.charge_no`、`medical_records.visit_id` 为**单据流水号**，必须全局唯一、绝不可复用。
  `drugs.code` 由应用层 `GetByCode(Unscoped)` 显式拦截以保历史可追溯（编码出现在历史处方/账目上）。
- **附带**：17 张软删表**零个** `deleted_at` 首列索引（model 声明了 `gorm:"index"` 但 DDL 只 `ADD COLUMN`），

### 11.3 该守卫的能力边界（重要）

守卫只能证明「字段名在后端**某个** struct 中存在」，不能证明「存在于**该端点返回的那个** DTO 中」。
问题 1 正是被这一点漏掉的——`drug_name` / `location_name` 在 `InventoryRow` 里存在，守卫放行，
但预警接口返回的是 `model.StockAlert`。因此：

- 跨表展示字段必须由仓储层 JOIN 后经**行 DTO** 返回，并**在后端补集成测试锁死**；
- 新增 `internal/service/alert_row_integration_test.go`（3 用例），
  对 `drug_name` / `location_name` / `days_left` 逐字段断言，并锁定「低库存预警 `days_left` 为 NULL 而非 0」
  （返回 0 会被前端误读为「今天到期」）。
- **反向验证已做**：分别把修复改回「缺 JOIN」与「套 EXTRACT」两种形态，确认测试均变红
  （分别报 `column stock_alerts.drug_name does not exist` 与 `extract(unknown, integer) does not exist`）。
