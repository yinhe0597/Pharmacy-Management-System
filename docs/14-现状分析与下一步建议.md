## 一、项目意图理解

以**药品进销存 + 处方调配**为核心的药房后端（Go + Gin + GORM + PostgreSQL），
一期独立运行，二期通过 `internal/service/port` 三接口（患者/库存/计价）扩展为「药房 + 诊疗」一体化系统。

核心设计意图（docs/01-04）：

| 设计原则 | 落地情况 |
|---------|---------|
| 库存正确性第一：行锁 + 条件更新 + 预占/实扣/释放 | ✅ 完整落地（`inventory_service.go`），集成测试覆盖并发不超卖 |
| 批号效期全流程 + FEFO | ✅ 完整落地（采购收货绑定 → 发药 FEFO → 退药按原批次回补） |
| 处方状态机唯一事实来源（Service 方法 + 版本号 + 审计日志） | ✅ 完整落地（`domain/prescription` + `prescription_audit_logs`） |
| 金额一律整数「分」 | ✅ 完整落地（`pkg/money`，无浮点） |
| 模块化单体 + 分层单向依赖 | ✅ 基本落地（Handler→Service→Repository；`port` 抽象就绪） |
| 7 角色分级权限（RBAC） | ❌ **未落地**（见 §三.1，当前实际为「登录即可操作」） |

## 三、审阅发现的问题（按严重度）

### 3.1 【架构级 · 高】角色权限（RBAC）实际未生效

**现状**：`internal/server/server.go` 定义了三个角色分组（`userAdmin` / `pharmacyMgmt` / `reportView`），
但除 `AuthHandler`（用户管理正确挂 admin-only）和库存库房新建（admin-only）外，
**其余全部 handler 的 `Register` 都把业务路由挂在 `authed` 组**（任意登录用户即可访问），
`pharmacyMgmt` / `reportView` 分组形同虚设。

**后果**（与 docs/03 §2 角色矩阵冲突）：
- 护士可开立处方（文档规定护士「无处方开立权」）
- 采购员/财务可改药品主数据、可做盘点调整、报损、拆零、调拨、采购收货
- 财务之外的角色均可看报表；报表权限组 `ReportAccess` 未使用
- 目前唯一的业务内权限校验是处方审核端点里的内联角色判断（`prescription_handler.go` Review）

**修复建议**：按 docs/03 §3 各模块接口清单的角色要求，把路由分别挂到对应分组
（写操作 → `PharmacyStaff`；处方开立 → `ClinicalStaff`；报表 → `ReportAccess`；
采购 → 采购员 + 药房人员；用户管理 → admin），并补一条「护士建处方 403」的 HTTP 层测试。

### 3.2 【功能缺陷 · 高】药师「退回医生」流程是死路（return 与 Update 冲突）

**现状**（`prescription_service.go`）：
- `Review(action=return)`：保持 `pending_review` **并保留预占**（v1.2 设计意图：医生可直接修改后重新提交）
- `Update`：要求 **无 active 预占**（`Count(active)>0` 即返回 3001）
- 而处方只有 submit 后才会被 review，submit 必然产生预占 → **被退回的处方永远无法修改**，
  医生只能作废重开，「退回修改」功能实际不可用（CHANGELOG v1.2 声称该流程可用）。

**修复建议**（二选一，推荐 A）：
- A：`return` 动作改为**释放预占**（与 reject 一致），保持 `pending_review`；医生修改后重新 submit 再预占。
  语义自洽，与 `Update` 的「无预占才可改」不变量一致；需同步更新 docs/03、docs/05、CHANGELOG 中「保留预占」的描述。
- B：`Update` 允许带预占修改，并同步重建/重算预占（复杂度高、易出 stale 预占，不推荐）。

### 3.3 【合规缺口 · 高】麻精处方「双人核对」未强制

**现状**：
- `ConfirmDispense` 的 `checker_id` 由请求体传入（缺省取当前用户），服务层**不校验**调配人 ≠ 核对人；
- 调配/发药/退药端点无角色校验，护士/采购员也可执行；
- 麻精发药「调配药师 + 核对药师双人签名、发药/核对必须为药师角色」（docs/04 §7）未强制。

**修复建议**：
- `Dispense` 记录调配人后，`ConfirmDispense` 校验 `checkerID != p.DispensingPharmacistID`（双人）；
- 对 `special_control_type ∈ {麻醉,精神}` 处方强制 `checker` 与调配人角色 ∈ {pharmacist, pharmacy_director, admin}；
- `checker_id` 不应由客户端传入，应从 JWT 取当前用户（核对即「当前操作人」）。

### 3.4 【功能缺口 · 高】v1.3 参考数据「数据入库、零代码接线」

**现状**：迁移 000015–000019 建了 5 张表并灌入 6,794 条种子数据，
但 **Go 代码中没有任何一处引用**（无 model / repository / handler / 路由，grep 验证为零匹配）。

**后果**：README 宣称的「诊断名称模糊搜索/自动补全、药品名称模糊搜索」等功能**不存在**；
ICD-10、集采、医保、非医保、耗材目录对系统用户完全不可见、不可查询。

**修复建议**（这是 v1.3 的收尾工作，工作量小、价值高）：
1. 新增 5 个只读查询端点：`GET /reference/diagnosis-codes?keyword=`、`/reference/vbp-drugs`、
   `/reference/nhsa-drugs`、`/reference/non-insurance-drugs`、`/reference/consumables`
   （分页 + keyword 模糊搜索 + py_code 拼音检索），供录入端自动补全；
2. `drugs` 表增加医保类别/集采批次关联列（`insurance_class`、`vbp_batch`）或在录入接口做目录匹配提示；
3. 补 5 张表的 model + 单元测试（keyword 搜索、分页）。

### 3.5 【中】交互引擎「患者级」能力无数据入口（能力就绪、不可达）

**现状**：引擎支持年龄/妊娠/哺乳/过敏史四类患者检查，但：
- `PrescriptionInput` 无 `patient_id` 字段，处方从不关联患者（`prescriptions.patient_id` 恒 0/NULL）；
- `SimplePatientService.GetAllergies` 恒返回空集（一期约定）；
- 处方无 `is_lactating` 入口。

**后果**：过敏史禁忌（3010）与哺乳期慎用（3011）在真实流程中**永远不会触发**（仅单测可达）；
年龄/妊娠检查可用（年龄字符串解析 + `is_pregnant` 字段）。

**修复建议**：
- 短期：处方录入增加 `patient_allergies`（过敏史文本）与 `is_lactating` 字段，录入即检查；
- 中期：落 `patients` 表（二期预告表之一），录入处方时选择/建档患者，`patient_id` 落库，
  过敏史持久化后自动参与审核——这正是 docs/05 §2 预留的二期接入点，可提前到一期收尾做。
