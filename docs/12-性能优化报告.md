# 12 性能优化报告

> 对象：一期热路径查询 ｜ 方法：索引覆盖核对 + `EXPLAIN` 验证 + 缺失索引补充

## 一、热路径清单与索引覆盖

| 热路径 | 查询特征 | 覆盖索引 | 结论 |
|--------|---------|---------|------|
| FEFO 发药选批次 | `inventory WHERE drug_id,location_id,status=1,quantity>reserved,expiry_date>=today ORDER BY expiry_date,received_at` | `idx_inventory_available (drug_id,location_id,expiry_date) WHERE status=1`；新增 `idx_inventory_fefo (drug_id,location_id,is_split,expiry_date) WHERE status=1` | ✅ 索引可用（小数据量下规划器倾向 Seq Scan 属正常） |
| 退药按明细查发药记录 | `prescription_dispense_records WHERE item_id=?` | **原缺失**；新增 `idx_dispense_item (item_id)` | ✅ 修复后走 Index Scan |
| 处方按状态查询 | `prescriptions WHERE status=?` | `idx_prescription_status` | ✅ |
| 处方明细 | `prescription_items WHERE prescription_id=?` | `idx_presc_items (prescription_id,drug_id)` | ✅ |
| 库存预占查询 | `stock_reservations WHERE ref_type,ref_id,status` | `idx_reservation_ref (ref_type,ref_id,status)` | ✅ |
| 库存流水（追溯/报表） | `inventory_transactions WHERE drug_id,created_at` | `idx_inv_txn_drug_time (drug_id,created_at)` | ✅ |
| 库存列表 | `inventory WHERE drug_id,location_id` | `idx_inventory_drug_loc` | ✅ |
| 近效期扫描（每日任务） | `inventory WHERE status=1 AND quantity>0` | `idx_inventory_expiry`（部分） | ✅ 全量扫描在千级批次规模可接受 |
| 专账查询/统计 | `special_drug_ledgers WHERE drug_id,created_at` | `idx_special_ledger (drug_id,created_at)` | ✅ |
| 采购单/收货单列表 | `WHERE supplier_id,status` | `idx_purchase_supplier`（采购单）；收货单无索引（单量小） | 🟡 可接受 |

## 二、EXPLAIN 验证

- 退药 `WHERE item_id=1`：修复前 `Seq Scan` → 修复后 `Index Scan using idx_dispense_item`。
- FEFO 选批次：小数据量下规划器选择 `Seq Scan`（行数极少的最优解）；`SET enable_seqscan=off` 验证
  `Index Scan using idx_inventory_available` 可用，规模化后自动走索引。
- 全部热路径均有对应索引，无全表扫描为主的业务查询。

## 三、本次新增索引（迁移 000004）

```sql
CREATE INDEX idx_dispense_item ON prescription_dispense_records (item_id);
CREATE INDEX idx_inventory_fefo ON inventory (drug_id, location_id, is_split, expiry_date) WHERE status = 1;
```

> 说明：`item_id` 索引同时修正了 Go 模型 `gorm:"index"` 与迁移 SQL 的不一致（此前只有 SQL 迁移生效）。
> `000001_init.up.sql` 已同步补充这两个索引，全新部署无需执行 000004。

## 四、其他性能观察与说明

1. **药品关键字检索** `generic_name/py_code ILIKE '%..%'`：默认 B-tree 不走索引（前导通配）。药房级数据量（≤数千）下可接受；如需规模化可启用 `pg_trgm` 扩展或引入全文检索。
2. **金额/单位**：全整数分运算，无浮点精度损耗；报表聚合为 SQL 侧 `GROUP BY`，由 `(drug_id, created_at)` 索引支撑。
3. **事务长度**：库存/处方关键操作均为单事务、短锁（行级），无事务内网络调用；未观测到锁等待异常。
4. **定时任务**：效期预警每日扫描全量 active 批次（千级），单次毫秒级；预警结果落库去重，避免重复告警。
5. **连接池**：`max_open_conns=20 / max_idle_conns=10 / lifetime=1h`，药房单点并发足够。

## 五、规模化建议（数据量 ≥10 万条时再评估）

- 药品/流水列表启用 `pg_trgm` 三角索引加速 ILIKE 检索。
- 库存流水表按 `created_at` 分区或归档冷数据。
- 报表由实时聚合改为每日物化（cron 落 `report_snapshots`）。
- 引入只读从库承接报表查询。
