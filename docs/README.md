## 一、项目定位

构建一套**以药品进销存 + 处方调配为核心**的专业药房管理系统（一期独立运行），
通过**接口抽象**预留诊疗扩展能力，二期无缝扩展为「药房 + 诊疗」一体化诊所管理系统。

- 一期不做医保规则、不做 Web 前端，交付完整的后端业务能力与 API 契约。
- 药房业务做深做透：批号效期全流程追踪、先进先出（FEFO）发药、库存预占/释放、
  拆零管理、特殊药品「五专」、处方全状态机。
- 二期通过 `IPatientService` / `IStockService` / `IPricingService` 等接口实现可插拔接入。

## 二、关键技术决策（本次细化修订）

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 数据库 | **PostgreSQL 14+** | 支持行级锁（`SELECT ... FOR UPDATE`）、高并发、复杂报表聚合；契合库存事务正确性要求 |
| 交付形态 | **纯后端 REST API + Swagger** | 一期聚焦业务正确性；前端二期独立开发 |
| Web 框架 | Gin | 生态成熟、中间件丰富、性能好 |
| ORM | GORM | 事务、软删除、自动迁移能力；配合 `clause.Locking` 实现行锁 |
| 数据库迁移 | golang-migrate（SQL 文件） | 生产级可控；SQL 为唯一事实来源 |
| 配置 | Viper（config.yaml + 环境变量覆盖） | 支持多环境 |
| 文档 | swaggo/swag（Swagger 注解） | 接口即文档 |
| 日志 | 标准库 `log/slog` | 结构化日志，零额外依赖 |
| 定时任务 | robfig/cron/v3 | 效期预警、过期锁定、下限预警、采购计划建议 |
| 鉴权 | JWT（golang-jwt/jwt）+ bcrypt | 记录发药人/审核人/操作人，支撑双人核对 |
| 金额 | int64（分）整数运算 | 避免浮点误差；拆零价按规则四舍五入 |

> 全文档中「金额一律以『分』为单位的整数存储与运算」，详见
> [04-领域模型与业务规则.md](04-领域模型与业务规则.md) 与 [06-开发规范.md](06-开发规范.md)。

## 三、总体开发思路

### 3.1 分层与模块

按「表示层（Handler）→ 领域服务层（Service）→ 仓储层（Repository）→ 领域模型（Domain）」四层构建，
数据模型（GORM Model）独立一层。Service 层通过 `port` 包暴露对外接口，二期在此替换实现。

```
yaofang/
├── cmd/server/            # 程序入口
├── internal/
│   ├── config/            # 配置加载
│   ├── model/             # GORM 数据模型（对应表结构）
│   ├── domain/            # 纯领域模型：状态机、金额、库存规则
│   ├── repository/        # 仓储实现（按模块分包）
│   ├── service/           # 领域服务（按模块分包）
│   ├── service/port/      # 对外接口（IPatientService/IStockService/IPricingService）
│   ├── handler/           # HTTP 处理器 + DTO（按模块分包）
│   ├── middleware/        # JWT、日志、恢复、请求ID
│   ├── scheduler/         # 定时任务
│   └── pkg/               # 通用组件（errs/money/pagination/...）
├── migrations/            # golang-migrate SQL 迁移文件
├── data/                  # 参考数据源文件（ICD-10 CSV/JSON、集采药品）
├── docs/                  # 本文档集
├── scripts/               # 运维/构建脚本
└── tests/                 # 集成测试
```

### 3.2 正确性优先的三个核心设计

1. **库存操作一律事务化 + 行级锁**：预占、实扣、释放在同一事务内对 `inventory` 行
   `SELECT ... FOR UPDATE`，并在 `UPDATE ... WHERE quantity >= x` 上做二次校验。
2. **批号效期贯穿全流程**：从采购收货（绑定批号/效期）到发药记录（记录批次）全程携带，
   发药按 FEFO（近效期先出）分配批次。
3. **处方状态机唯一事实来源**：状态流转只通过 Service 层方法触发，所有变更写
   `prescription_audit_logs`，支持并发保护（行锁 + 版本号）。

### 3.3 一期交付物

- 可运行的药房后端服务（Gin API + Swagger 文档）
- PostgreSQL 迁移脚本（golang-migrate）
- 一期全部业务模块：药品、供应商、采购入库、库存、处方调配、特殊药品、药学服务、报表
- 二期预留接口文档与本接口文档（供二期开发直接使用）
- 单元/集成/契约测试 + 测试报告
- 部署运维文档

## 四、与二期（诊疗模块）的衔接

一期把以下「能力出口」做成**标准接口**，二期替换实现即可无缝接入：

| 能力 | 一期实现 | 二期扩展 | 详见 |
|------|---------|---------|------|
| 患者标识 | 完整患者档案（`patients` + 过敏史，`IPatientService` 完整实现） | 就诊/病历/检查等临床档案 | [05](05-二期预留接口设计.md) |
| 处方开立 | 药房端手工录入（支持关联患者档案） | 医生端开立传入 | [03](03-接口设计.md) |
| 库存预占/实扣/释放 | 药房内部调用 | 诊疗模块直接调用 | [05](05-二期预留接口设计.md) |
| 计价 | 药费 + 计费闭环（发药生成/退药冲正） | 挂号费/诊疗费/药费合并 | [05](05-二期预留接口设计.md) |
