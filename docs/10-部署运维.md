# 10 部署运维文档

> 本文覆盖：部署形态选型（裸机 / Docker Compose / K8s）、镜像构建、健康检查、
> 数据库连接池配置说明、日志聚合方案、CI/CD 流水线、备份与升级。

## 一、部署形态总览

单体服务，三种部署形态按团队条件选择，后端逻辑完全一致（配置走环境变量 `YF_` 前缀）：

| 形态 | 适用场景 | 入口 |
|------|---------|------|
| **裸机 + systemd** | 无 Docker / 单机生产（当前推荐） | `deploy/yaofang.service` + `bin/yaofang` |
| **Docker Compose 全栈** | 有 Docker 的服务器 / 内部环境 | `docker-compose.yml`（db + migrate + api + web） |
| **Kubernetes** | 云原生 / 需要弹性伸缩 | `deploy/k8s/*.yaml` |

版本信息在构建期注入（`/version` 与启动日志可见）：`go build -ldflags "-X yaofang/internal/version.Version=..."`。

## 二、环境要求

| 组件 | 版本 | 说明 |
|------|------|------|
| Go | ≥ 1.26.5（与 go.mod 一致） | 编译环境 |
| PostgreSQL | ≥ 14（建议 16） | 数据库 |
| Docker / Compose（可选） | 容器化部署时 | 见 §6 |
| Kubernetes（可选） | ≥ 1.25 | 见 §8 |

## 三、构建

```bash
# 本地构建（注入版本信息）
CGO_ENABLED=0 go build -trimpath \
  -ldflags "-s -w \
    -X yaofang/internal/version.Version=v1.4.0 \
    -X yaofang/internal/version.Commit=$(git rev-parse --short HEAD) \
    -X yaofang/internal/version.BuildTime=$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  -o bin/yaofang ./cmd/server

# 交叉编译（Linux amd64，无 Docker 目标机部署用）
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build ... -o bin/yaofang-linux-amd64 ./cmd/server
```

## 四、配置

`configs/config.example.yaml` 为样例（复制为 `config.yaml` 用于本地），生产一律用环境变量覆盖：

| 环境变量 | 说明 |
|---------|------|
| `YF_SERVER_PORT` / `YF_SERVER_MODE` | 端口 / `release` |
| `YF_DATABASE_HOST/PORT/USER/PASSWORD/NAME/SSLMODE` | 数据库连接（云数据库 `SSLMODE=require`） |
| `YF_DATABASE_MAX_OPEN_CONNS/MAX_IDLE_CONNS/CONN_MAX_LIFETIME/CONN_MAX_IDLE_TIME` | 连接池参数，见 §9 |
| `YF_AUTH_JWT_SECRET` | JWT 密钥（生产必改，≥32 字符随机） |
| `YF_LOG_LEVEL/FORMAT/FILE` | 日志级别（debug/info/warn/error）、格式（text/json）、文件路径 |
| `YF_SCHEDULER_ENABLED` | 定时任务开关 |

连接池/日志配置均有钳制兜底：非法值自动回退默认（`max_idle ≤ max_open` 强制成立），不会因配置错误崩溃。

## 五、健康检查端点（负载均衡 / 容器编排感知服务状态）

| 端点 | 类型 | 语义 | 失败时 |
|------|------|------|--------|
| `GET /healthz` | 存活探针 | 进程存活即 200；进入优雅关闭后返回 503 | 编排重启实例 |
| `GET /readyz` | 就绪探针 | **校验数据库连通性**（2s 超时），连通才 200 | 编排摘除流量 |
| `GET /version` | 版本信息 | version / commit / build_time / go_version | — |

要点：
- 探针无鉴权、不写访问日志（避免刷屏告警）；
- **滚动发布/摘流量**：收到 SIGTERM 时先标记关闭（`/healthz` 转 503），再排空存量请求（10s 超时），保证负载均衡先摘后杀；
- K8s 使用示例见 `deploy/k8s/api-deployment.yaml`（livenessProbe + readinessProbe）；
- 运维探活：`curl -fsS http://localhost:8080/readyz`。

## 六、容器化部署（Docker）

> 本机无 Docker 也能先落地本套文件，待有环境直接构建。

### 6.1 镜像清单

| 镜像 | 构建方式 | 说明 |
|------|---------|------|
| 后端 | `docker build -f Dockerfile .` | 多阶段：Go 1.26.5 静态编译 → Alpine，非 root 运行 |
| 前端 | `docker build pharmacy-web` | Vite 构建 → Nginx 托管 SPA + `/api` 反代 |
| 迁移 | `docker build -f deploy/Dockerfile.migrate .` | 内置全部 migrations，启动即执行 |

后端镜像不含任何配置/密钥（全环境变量）；版本信息经 `--build-arg VERSION/COMMIT/BUILDTIME` 注入。

### 6.2 一键全栈

```bash
docker compose up -d --build        # db → migrate → api → web
# 访问：前端 http://localhost:8088 ，API http://localhost:8080/readyz
docker compose down                 # 停止（加 -v 删数据卷）
make docker-up / docker-down        # 等价快捷方式
```

`docker-compose.yml` 内置依赖等待与健康检查：`api` 依赖 `db` 健康、`web` 依赖 `api` 健康后才启动；`api` 自带 `/readyz` healthcheck。

### 6.3 镜像推送与拉取

CI 流水线（§11）自动构建并推送三枚镜像到 GHCR；手动推送：

```bash
docker build -t ghcr.io/<owner>/<repo>/yaofang-api:latest .
docker push ghcr.io/<owner>/<repo>/yaofang-api:latest
```

## 七、无 Docker 裸机部署（systemd）

适合当前无 Docker 的服务器：

```bash
# 1. 上传二进制与迁移（或直接 git clone 后在服务器编译）
mkdir -p /opt/yaofang/bin
scp bin/yaofang-linux-amd64 user@host:/opt/yaofang/bin/yaofang
scp -r migrations user@host:/opt/yaofang/

# 2. 生产环境变量文件（systemd EnvironmentFile）
sudo mkdir -p /etc/yaofang
sudo tee /etc/yaofang/env >/dev/null <<'EOF'
YF_SERVER_MODE=release
YF_DATABASE_HOST=127.0.0.1
YF_DATABASE_PORT=5432
YF_DATABASE_USER=yaofang
YF_DATABASE_PASSWORD=***
YF_DATABASE_NAME=yaofang
YF_AUTH_JWT_SECRET=***（≥32 位随机）
YF_LOG_FORMAT=json
YF_LOG_LEVEL=info
EOF
sudo chmod 600 /etc/yaofang/env

# 3. 安装 systemd 单元并启动
sudo cp deploy/yaofang.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now yaofang

# 4. 执行迁移（幂等，可重复）并探活
for f in migrations/*.up.sql; do PGPASSWORD=*** psql -h 127.0.0.1 -U yaofang -d yaofang -v ON_ERROR_STOP=1 -f "$f"; done
curl -fsS http://localhost:8080/readyz
```

## 八、Kubernetes 部署

`deploy/k8s/` 下按序号应用（先建 Namespace 与 Secret）：

```bash
kubectl apply -f deploy/k8s/00-namespace.yaml
kubectl apply -f deploy/k8s/api-secret.yaml      # 先替换占位密钥！
kubectl apply -f deploy/k8s/api-configmap.yaml   # 先替换数据库地址
kubectl apply -f deploy/k8s/api-deployment.yaml deploy/k8s/api-service.yaml
kubectl apply -f deploy/k8s/web-deployment.yaml deploy/k8s/web-service.yaml
kubectl apply -f deploy/k8s/ingress.yaml         # 可选
kubectl apply -f deploy/k8s/api-hpa.yaml         # 可选：CPU 70% 水平伸缩 2-8 副本
```

**升级流程**（先迁移后滚动发布）：

```bash
# 1. 执行迁移 Job（幂等）
kubectl delete job yaofang-migrate -n yaofang 2>/dev/null || true
kubectl apply -f deploy/k8s/migrate-job.yaml
kubectl wait --for=condition=complete job/yaofang-migrate -n yaofang --timeout=300s

# 2. 滚动发布新镜像（readinessProbe 保证新 Pod 就绪才继续）
kubectl set image deployment/yaofang-api api=registry.example.com/yaofang-api:v1.4.0 -n yaofang
kubectl rollout status deployment/yaofang-api -n yaofang
```

注意：多副本时连接池要按实例分摊（ConfigMap 中 `MAX_OPEN_CONNS=30` 对应 2 副本 ≈ 60 连接，见 §9）。

## 九、数据库连接池配置说明（高并发）

### 9.1 参数含义与默认值

| 参数 | 默认 | 含义 | 建议 |
|------|------|------|------|
| `max_open_conns` | 20 | 最大同时打开的连接数 | ≤ 数据库可分配份额，见下方公式 |
| `max_idle_conns` | 10 | 最大空闲连接数（0 = 不保留） | 建议 ≤ max_open_conns 的 50% |
| `conn_max_lifetime` | 1h | 连接最大存活时长 | 必须 **小于** 数据库/网关会话超时（云 RDS 常见 4h） |
| `conn_max_idle_time` | 30m | 空闲连接回收时长 | 30m~1h，防止空闲连接被服务端提前断开 |

非法值自动钳制（`idle > open` 时收敛、零值回退默认），不会因配置错误起不来。

### 9.2 高并发容量公式

```
单实例 max_open_conns ≈ (PG max_connections − 管理/备份预留) ÷ 应用实例数
```

例：PG `max_connections = 200`，预留 40（pg_dump、维护、其他服务），3 个 API 实例 →
每实例 `max_open_conns = (200 − 40) ÷ 3 ≈ 53`，可设 50；`max_idle_conns = 25`。

⚠️ 常见事故：**实例数 × max_open_conns > PG max_connections**，导致 `too many connections`。
扩容/缩容实例时务必同步调整连接池。

### 9.3 监控与排障

```sql
-- 当前连接数与来源
SELECT count(*), state, usename FROM pg_stat_activity
WHERE datname = 'yaofang' GROUP BY state, usename;

-- 最长事务（排查锁/长事务占连接）
SELECT pid, now() - xact_start AS age, state, query
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY age DESC LIMIT 10;

-- 等待锁的会话
SELECT pid, wait_event_type, wait_event, query FROM pg_stat_activity WHERE wait_event_type = 'Lock';
```

日志侧观察：`database/sql` 连接获取超时表现为 `sql: database is closed` / `connection pool exhausted`（当前 GORM 日志级别 Warn 会打印慢 SQL，生产可调 `gormlogger` 级别）。

## 十、日志聚合方案（生产问题排查）

### 10.1 现状：结构化日志

- 统一 `log/slog` 输出，**所有行带 `service=yaofang` 与 `request_id`**（访问日志、业务日志、panic 均含）；
- 生产建议 `YF_LOG_FORMAT=json`：每行一条 JSON，采集端可直接解析，无需正则；
- 容器内日志只写 **stdout**（`log.file` 留空），由容器运行时/Promtail 采集；
- 裸机可用 `log.file=/var/log/yaofang/yaofang.log` 落盘，配合 `logrotate` 轮转（下方样例）。

### 10.2 方案 A：Loki + Promtail + Grafana（推荐，轻量）

```bash
docker compose -f compose.logging.yml up -d     # 与主编排同目录
# Grafana http://localhost:3000（admin/admin123，首次登录改密）
# 添加 Loki 数据源 http://loki:3100，Explore 查询：
#   {container_name=~"yaofang.*"}                     # 全部服务日志
#   {service="yaofang-api"} |= "error"                # 按服务+关键字
#   {service="yaofang-api"} |= "request_id=abc123"    # 按请求ID串联
```

Promtail 配置 `deploy/logging/promtail-config.yml`：docker_sd 自动发现容器（按 compose 项目名过滤），裸机场景可用 journald / 文件采集（配置内含注释样例）。

### 10.3 方案 B：ELK / EFK

结构同 10.2，将 Loki 换成 Elasticsearch：Filebeat（容器/文件采集）→ ES → Kibana。
适合已有 ES 运维经验的团队；代价是资源占用更高。

### 10.4 方案 C：云厂商日志服务

- 阿里云 SLS / 腾讯云 CLS / 华为云 LTS：容器场景直接接 stdout（如阿里云 ACK 的 logtail-ds），
  裸机装 agent 采集 `/var/log/yaofang/` 或 journald；
- 优点：免运维、自带告警（错误率/关键字告警可配置）。

### 10.5 裸机落盘 + logrotate（无任何采集端时的兜底）

```
# /etc/logrotate.d/yaofang
/var/log/yaofang/yaofang.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

### 10.6 可观测建议

- 告警阈值参考：`http_request` 5xx 比例、`panic_recovered` 计数、`readyz` 503；
- 每次发布带版本号（`/version`），日志里 `version` 字段可回溯发布前后行为差异。

## 十一、CI/CD 流水线

| 流水线 | 触发 | 内容 |
|--------|------|------|
| `.github/workflows/ci.yml` | push/PR | 迁移 + 编译（含版本注入）+ vet/gofmt + golangci-lint + 单元/集成测试 + 覆盖率门槛 + Swagger 一致性 |
| `.github/workflows/frontend-ci.yml` | push/PR | npm ci + type-check + lint + format + build |
| `.github/workflows/docker-image.yml` | main / v* 标签 / 手动 | 构建并推送 后端/前端/迁移 三枚镜像到 GHCR（多架构 amd64+arm64） |
| `.github/workflows/deploy.yml` | 手动 | **裸机部署**：交叉编译 → SCP 上传 → 迁移 → 重启 systemd → `/readyz` 探活 |

> ⚠️ 仓库当前托管在 **Gitee**，GitHub Actions 不生效。两条路径任选：
> 1. 镜像到 GitHub（推荐，直接使用以上流水线）；
> 2. 在 Gitee 使用 Gitee Go 流水线（配置思路相同：编译 → 推送镜像 / SSH 部署），
>    或本机手动执行 §7 步骤。本仓库的 workflow 文件同时是 Gitee Go 的配置参照。

## 十二、数据库备份

```bash
# 每日凌晨备份（可入 crontab）
pg_dump -U yaofang -h localhost -d yaofang -Fc -f /backup/yaofang_$(date +\%Y\%m\%d).dump

# 恢复
pg_restore -U postgres -d yaofang --clean /backup/yaofang_xxx.dump
```

建议：定时备份 + 异地保留 30 天；变更前先备份。

## 十三、升级步骤（三形态通用）

1. `git pull` 拉取新版本，审阅新增 `migrations/` 迁移文件；
2. 备份数据库（§12）；
3. 按版本顺序执行迁移（裸机 §7 / Compose `docker compose run --rm migrate` / K8s §8 Job）；
4. 发布新版本（裸机重启 systemd / Compose `docker compose up -d --build` / K8s 滚动发布）；
5. `curl -fsS http://localhost:8080/readyz` 探活，观察日志无 `panic_recovered`/`internal_error`。

## 十四、运维检查清单

| 检查项 | 方式 |
|--------|------|
| 探活 | `GET /healthz`（存活）、`GET /readyz`（就绪，含 DB 连通性） |
| 版本核对 | `GET /version` 与发布记录比对 |
| 日志 | 聚合平台检索 `service="yaofang-api"`，按 `request_id` 串联单次请求 |
| 定时任务 | 观察日志 `scheduler_*` 是否正常执行 |
| 连接池 | §9.3 SQL 监控连接数与长事务 |
| 磁盘/备份 | 日志轮转是否生效、备份任务是否成功 |
