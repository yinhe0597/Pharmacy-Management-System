# 07 测试方案

> 实际落地为五层：单元测试（domain/pkg/config/middleware）→ SQL 构建断言（DryRun，无需数据库）→
> 集成测试（真实 PostgreSQL 全链路）→ 契约测试（预留接口）→ 前端单测（vitest）。
> 后端单元/集成、SQL 断言与前端单测均纳入 CI。

---

## §1 测试环境

| 层级 | 依赖 | 工具/位置 |
|------|------|----------|
| 单元 | 无 | `go test`（标准库 testing，无 testify/mock 依赖）：`internal/domain/*`、`internal/pkg/*`、`internal/config`、`internal/middleware`、`internal/service` 纯函数（CSV 编码/保留期解析） |
| SQL 构建断言 | 无（DryRun 仅构建语句不执行） | `internal/repository/concurrency_sql_test.go`（upsert/条件更新/差异口径） + `report_s7_sql_test.go`（归档 CTE 原子性；注：Raw+Scan 的 SELECT 在 DryRun 下被 gORM 短路，SELECT 口径由集成环境覆盖） |
| 集成 | 真实 PostgreSQL（`make db-up` 起库并迁移） | `go test -tags=integration ./internal/service/`，用例内 `setupTestDB` |
| 契约 | 同上 | `internal/service/contract_test.go`（模拟诊疗模块调用 `port` 接口） |
| 前端 | Node ≥ 20 | `npm run test`（vitest）：`pharmacy-web/src/**/*.test.ts` |

- 集成测试连接由 `YF_TEST_DB_*` 环境变量注入（默认 `127.0.0.1/yaofang`），测试密钥由用例内
  `t.Setenv("YF_AUTH_JWT_SECRET", ...)` 注入，**不依赖本地 `configs/config.yaml` 与外部环境**（CI 可直接跑）。
- 每个用例先 `setupTestDB` 清空业务表（`TRUNCATE ... RESTART IDENTITY CASCADE`，清单为包变量
  `testCleanupTables`，覆盖库存/处方/采购/盘点/拆零/领用/专账/患者/就诊/结算/通知/审计等 40 表），保证**用例顺序无关**；
  `TestCleanupCoversAllTables` 守护：库中真实表必须登记在清理清单或静态表清单（种子/引用/基础设施），
  新增业务表未登记则守护失败；涉及盘点的用例结束需取消盘点（`counting` 状态会禁止出入库）。
- 时间相关测试：`domain` 函数接收 `today time.Time` 参数，避免依赖系统时钟。

## §2 单元测试重点（对应需求「六、测试要点」）

### 2.1 库存预占与释放的事务完整性
- 预占成功：`reserved_quantity` 增加、可用量减少、`stock_reservations` 出现 active 记录。
- 预占不足：返回 shortage 明细，库存行不变化。
- 释放：`reserved_quantity` 还原、预占记录置 released。
- 实扣：`quantity` 与 `reserved_quantity` 同步减少，流水类型正确。
- 并发预占/实扣（多 goroutine 打同一批次）：最终不超卖、无负库存（`TestConcurrentReserveNoOversell`）。
- 并发入库同一新批次：原子 upsert 全部成功且数量精确累加（`TestConcurrentStockInSameNewBatch`）。
- 采购收货防超收：创建期在途校验 + 完成期条件更新双护栏（`TestPurchaseReceiveOverReceiveGuards`）。

### 2.2 效期计算与过期判定
- `DaysToExpiry` 边界：当天到期、次日到期、已过期。
- 近效期阈值（=预警天数、-1、+1）的告警生成。
- 过期锁定任务：`expiry_date < today` → status=2，且不再被发药选中。

### 2.3 拆零数量换算与精度
- `1盒(24粒)` 拆零 → 拆零行 +24粒、整盒行 -1盒、两条流水。
- 多次拆零合并到同一拆零行。
- `SplitPrice` 舍入：`2400/24=100`、`2500/24≈104.17→104`（半入）、`2499/24≈104.125→104`。
- **已知取整残差**：1 盒 24 片、盒价 1000 分 → 单片 42 分 → `24×42=1008` 分（高 8 分），单测固化
  （`TestSplitPriceRoundingDrift`，见 docs/04 §1.1）。
- `ItemAmount` 边界：`packSize=0/-1/1` 不除零（`TestItemAmountEdgeCases`）。
- `money.ParseYuan` 十进制精确解析（`12.345 → 1235`，不走浮点）。

### 2.4 处方状态流转逻辑
- 合法流转：pending→reviewed_passed→dispensing→dispensed→returned。
- 非法流转拒绝：dispensing→pending_review、dispensed→dispense 等返回 `3001`。
- 并发流转（两 goroutine 同时 confirm）：版本号冲突，一方成功一方 `9005`。
- 每次流转写入 `prescription_audit_logs`。

### 2.5 特殊药品管控规则
- 麻精处方缺卡号/诊断 → `4001`。
- 非药师角色发麻精药 → `9003`。
- 单张处方剂量超限量 → 拦截。
- 发药联动写 `special_drug_ledgers`；空安瓿回收核对落库 `verified_by` 且重复核对拒绝（`9005`）。

### 2.6 审核规则
- 配伍禁忌（level=1）拦截 `3003`；慎用（level=2）仅提示。
- 极量检查：单次/日极量超限 `3002`。
- 重复用药（同通用名两行）提示并可备注通过。

### 2.7 中间件与安全基线
- JWT：签发/解析、算法强制 HMAC（拒 `alg=none`）、过期拒绝（`internal/pkg/auth`）。
- RBAC：`RequireRoles` 白名单（未挂 Auth 时安全返回 403，不 panic）。
- CORS：白名单为空**不下发任何 CORS 头**（fail-closed）、`*` 放行、精确匹配、预检 204（`cors_test.go`）。

## §3 集成测试场景（对应需求「六、集成测试」）

1. **并发发药正确性**：两个处方并发对同一批次发药，总扣减 = 两处方实扣，无负库存，无超卖。
2. **效期预警准确性**：构造不同效期批次，跑定时任务，断言 `stock_alerts` 生成与状态锁定正确；
   重复执行不产生重复预警（open 状态部分唯一索引 + `ON CONFLICT DO NOTHING`）。
3. **退药恢复**：部分退/整方退后，原批次 `quantity` 回补、流水类型 `dispense_return`、处方状态正确；
   拆零记录优先命中（散片退药不受整盒倍数约束干扰）。
4. **全链路**：采购入库（批次 A）→ 处方开立 → 审核 → 调配（FEFO 选到批次 A）→ 发药确认 → 库存扣减 → 退药回补。
5. **拆零链路**：整盒入库 → 拆零 → 拆零处方发药 → 单价/金额正确。
6. **调拨链路**：药库→药房调拨，双端库存与流水正确；可用量不足整体失败；反向并发调拨不死锁。
7. **盘点链路**：建盘点单 → 录入实盘 → 差异调整 → 库存修正、流水 `stocktake_adjust`；盘点期间禁止出入库；
   `stocktake_items.difference` 口径 = 实盘 − 账面（`TestStocktakeDifferencePersisted`）。
8. **特殊药品全流程**：专用处方 → 双人核对发药 → 专账/空安瓿回收登记。

## §4 SQL 构建断言（DryRun，无需数据库）

用于守护「并发正确性关键 SQL」不被回退（`internal/repository/concurrency_sql_test.go`）：

| 用例 | 断言 |
|------|------|
| `UpsertAddQuantity` | 生成 `INSERT ... ON CONFLICT (五键) DO UPDATE ... RETURNING`，且**不含**先查后插（SELECT） |
| `UpdateReceivedWithinLimit` | 累加与超收护栏在**同一条 UPDATE**（`received_quantity + ? <= quantity`），无 SELECT |
| `UpdateCounted` | 差异列按 `? - book_quantity` 计算（口径 = 实盘 − 账面） |

> 动机：PostgreSQL 唯一键冲突后事务进入 `aborted`（25P02），「先查后插 + 冲突后回退」必然失败；
> 该层用零依赖方式把这类修复钉住。

## §5 契约测试（预留接口）

> 以「模拟诊疗模块」身份调用 `port` 接口，验证入参/出参与 [05-二期预留接口设计.md](05-二期预留接口设计.md) 一致。

| 用例 | 断言 |
|------|------|
| `ReserveStock` 入参合法 → 返回 reservations，库存被预占 | 出参结构、shortage=0 |
| `DispenseAndReduceStock` → 库存实扣 | 出参无 error，流水存在 |
| `CancelReservation` → 库存还原 | 预占释放 |
| `GetDrugAvailability` → 各库可用量 | 字段完整、可用 = 总量-预占 |
| `IPatientService`（简易版） | 空实现不报错、注册/查询行为符合一期约定 |
| `IPricingService.CalculatePrescriptionAmount` | 药费明细金额正确 |

**契约守则**：接口签名与 DTO 结构任何改动须同步更新本文档 + [05](05-二期预留接口设计.md) + Swagger，且跑通契约测试。

## §7 覆盖率与 CI 门槛

| 门槛 | 值 | 落地方式 |
|------|----|---------|
| domain 包覆盖率 | ≥ 85%（实测 92.5%） | `scripts/check_coverage.sh`（CI 执行，合并 enum/prescription/rule/interaction 四包） |
| service 覆盖率 | ≥ 35%（实测 41.5%） | 同上（集成口径，`-coverpkg=./internal/service/...,./internal/repository/...`） |
| repository 覆盖率 | ≥ 20%（实测 24.6%） | 同上 |
| handler 覆盖率 | ≥ 10%（实测 12.1%） | 同上（HTTP 层集成测试口径） |
| middleware / pkg.auth / pkg.money / config | ≥ 30% / 60% / 60% / 30% | 同上（单元口径） |
| golangci-lint | 0 error | `.golangci.yml`（govet/errcheck/staticcheck/ineffassign/unused/gosimple/gocyclo/misspell） |
| gofmt / go vet | 0 差异 | CI `gofmt -l` + `go vet ./...` |
| 单元 + 集成测试 | 全绿才可合入 | `go test ./...` + `go test -tags=integration ./internal/service/ ./internal/handler/`（CI 带 PostgreSQL 16 服务） |
| 前端 | 全绿才可合入 | `vitest` + `vue-tsc` + `eslint` + `prettier --check` + `vite build`（`frontend-ci.yml`） |
| Swagger 一致性 | 无 diff | CI 重新生成后 `git diff --exit-code docs/` |
| 供应链漏洞 | 0 可达 | `govulncheck ./...`（当前 Go 1.26.6 下 0 可达）；前端 `npm audit` 0 漏洞 |

> **覆盖率口径提示**：`-coverpkg` 必须精确限定到目标包；若写成 `./internal/...`（包含测试包自身），
> Go 会对同一包做「被测包 + coverpkg」双重插桩，语句总数翻倍、百分比失真（实测 service 41.5% 会被算成 21.5%）。

CI 流水线：`迁移 → 编译（含版本注入）→ vet/gofmt → golangci-lint → 单元测试 → 覆盖率门槛（单元 + 集成口径）→
集成测试（真实 PG）→ Swagger 一致性`；前端独立流水线：`install → type-check → lint → prettier → vitest → build`。
